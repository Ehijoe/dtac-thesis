\section{Introduction}
The primary aim of this research is to design, implement, and evaluate a dynamic, heuristic caching architecture—the Dynamic Traffic-Aware Cache (DTAC)—to mitigate the severe cache pollution caused by Artificial Intelligence (AI) scrapers, thereby preserving the temporal locality and efficiency of web infrastructure for legitimate human users. To achieve this, the study employs an experimental systems research design that seamlessly bridges software engineering with controlled performance benchmarking.

This chapter outlines the methodology and procedures utilized to construct and validate the proposed system. It is structured to guide the reader through the complete research lifecycle, from initial system design to final metric evaluation. Section 3.2 provides a high-level overview of the research design and system architecture, detailing the data flow between the Heuristic Proxy and the DTAC engine. Section 3.3 outlines the development environment, explicitly stating the hardware specifications, software stack, and simulation tools required to ensure the reproducibility of the study.

The core implementation is divided into two distinct phases. Section 3.4 describes Phase 1: The System Development Sandbox, which details the algorithmic coding of the passive AI-score generator and the specific modifications made to the standard Least Recently Used (LRU) eviction logic. Section 3.5 outlines Phase 2: Workload Simulation and Data Generation, explaining the mathematical models used to synthesize both legitimate Zipfian human traffic and non-recurring automated scan patterns. Finally, Section 3.6 details the experimental setup and the controlled benchmarking procedures used to test the prototype, while Section 3.7 defines the specific mathematical and performance metrics—such as Cache Hit Ratio (CHR) and computational latency—used to evaluate the success of the DTAC architecture.

The core of the experimental setup relies on a two-stage architectural model positioned between the incoming traffic and the origin web server, as depicted in Diagram 2. The system is composed of the following primary components:

\begin{itemize}
    \item \textbf{The Heuristic Proxy (``The Brains''):} This component intercepts incoming traffic and serves as the analytical engine. It is subdivided into two distinct modules:
    \begin{itemize}
        \item \textit{State Manager:} This module tracks sequential request patterns across sessions. Crucially, it monitors structural anomalies, such as the absence of subsequent \texttt{favicon.ico} requests that typically follow legitimate human browser interactions.
        \item \textit{AI-Score Generator:} Utilizing the data from the State Manager, this module calculates and outputs a continuous probability score ranging from 0.0 to 1.0. This score probabilistically quantifies whether the incoming HTTP request originated from an automated AI scraper.
    \end{itemize}
    \item \textbf{The DTAC Cache:} Positioned directly upstream of the origin server, this caching engine receives both the standard HTTP request and the newly appended AI-score. It consists of:
    \begin{itemize}
        \item \textit{DTAC (AI-Aware LRU):} The core memory management engine. It utilizes a modified Least Recently Used algorithm that factors the appended AI-score into its admission and eviction logic, dynamically penalizing highly probable bot traffic.
        \item \textit{Metrics Tracker:} An integrated monitoring tool that continuously logs cache hits, misses, and overall hit rates to generate the raw data required for the final Performance Evaluation phase.
    \end{itemize}
\end{itemize}

\subsection{Data Flow and Request Lifecycle}
The lifecycle of an individual network request follows a strict, unidirectional path through the architecture (see Diagram 2, \texttt{Gemini\_Generated\_Image\_fuhyknfuhyknfuhy.png}):

\begin{enumerate}
    \item \textbf{Ingestion:} Incoming HTTP requests are dispatched from the ``Simulated Web Logs'' and arrive at the Heuristic Proxy.
    \item \textbf{Scoring and Forwarding:} The proxy's State Manager and AI-Score Generator evaluate the request, append the calculated 0.0--1.0 probability score to the payload, and forward the combined ``Request + AI-Score'' to the DTAC Cache.
    \item \textbf{Cache Evaluation:}
    \begin{itemize}
        \item \textit{Cache Hit:} If the DTAC Cache already holds the requested resource in memory, it bypasses the origin server and directly returns the cached resource to the client.
        \item \textit{Cache Miss:} If the resource is not found, or if it was previously evicted due to cache pressure, the DTAC Cache forwards the raw request to the Origin Web Server.
    \end{itemize}
    \item \textbf{Retrieval and Storage:} The Origin Web Server processes the request and returns the fresh resource to the DTAC Cache. The AI-Aware LRU algorithm evaluates the object's AI-score to determine where (or if) it should be stored in the cache hierarchy, potentially evicting older content to make room, before ultimately returning the resource to the client.
\end{enumerate}

\section{Development Environment and Tools}
To ensure the reproducibility of the study and guarantee that the system can process high-volume network traffic with minimal latency, the hardware and software environments were strictly defined.

\subsection{Hardware Specifications}
To ensure the development process was practically accessible while maintaining rigorous, controlled conditions for the final performance evaluation, the hardware specifications were divided into two distinct environments:

\begin{itemize}
    \item \textbf{System Development Sandbox (Local Environment):} The initial coding, functional acceptance testing, and algorithm debugging (Phase 1) were conducted on a standard consumer laptop. This environment featured a 12th Gen Intel\textsuperscript{\textregistered} Core\textsuperscript{\texttrademark} i5-1235U processor, 16 GB of RAM, and a standard Solid State Drive (SSD). These baseline specifications were sufficient for compiling Rust binaries, verifying the memory safety of the DTAC algorithm, and testing low-volume traffic routing without risking system crashes.
    \item \textbf{Benchmarking and Evaluation Track (Cloud Bare-Metal Server):} To ensure the experimental results were not skewed by local thermal throttling, background operating system processes, or hardware bottlenecks, the final high-volume workload simulations (Phase 2) were executed on a dedicated cloud bare-metal server. This controlled environment featured an 8-core processor, 32 GB of DDR4 RAM, and a high-speed NVMe SSD. These robust specifications guaranteed that the system could comfortably accommodate massive in-memory cache data structures and highly concurrent log replays without triggering operating system swap space, thereby providing accurate, uninflated latency and hit-rate metrics.
\end{itemize}

\subsection{Software Stack and Programming Language}
The Heuristic Proxy and the Dynamic Traffic-Aware Cache (DTAC) were developed entirely in Rust. Rust was explicitly selected for this architecture because it successfully bridges the gap between high-level safety and low-level system performance.

\begin{itemize}
    \item \textbf{Memory Safety:} In traditional low-level languages like C and C++, developers have direct control over memory, which allows for exceptional speed but introduces severe vulnerabilities such as dangling pointers, memory leaks, and buffer overflows. Rust eliminates these bugs at compile time through its strict ``ownership'' and ``borrowing'' rules, guaranteeing memory safety without relying on a runtime garbage collector.
    \item \textbf{High Performance:} Because it compiles directly to machine code and lacks the overhead of garbage collection pauses, Rust achieves low-latency execution speeds comparable to C and C++. This is critical for building a network proxy and cache, where calculating the $\mathcal{O}(1)$ AI-score must not introduce latency that outweighs the time saved by caching.
    \item \textbf{Concurrency:} Rust's type system prevents data races in multi-threaded environments, enabling ``fearless concurrency'' when processing simultaneous HTTP requests.
\end{itemize}

The standard library's \texttt{HashMap} and custom doubly linked list structures were used to build the core LRU memory management engine. Furthermore, the asynchronous networking framework \texttt{tokio} (a standard crate in the Rust ecosystem) was utilized to handle the high-throughput, non-blocking I/O operations required to ingest the simulated HTTP requests.

\subsection{Simulation and Log Replay Tools}
Because testing against a live production server introduces unpredictable variables, the workloads were completely simulated. Custom Rust binary scripts were developed for data generation and log replay:

\begin{itemize}
    \item \textbf{Data Generator:} A script designed to output synthetic HTTP logs. It mathematically blends Zipf-distributed human requests (mimicking temporal locality) with uniform, non-recurring automated bot scans.
    \item \textbf{Log Replayer:} A highly concurrent script that reads the generated synthetic logs from the NVMe SSD and fires them at the Heuristic Proxy over the local network interface (\texttt{localhost}), allowing the system to process thousands of requests per second under controlled, verifiable conditions.
\end{itemize}

\section{System Implementation}
This section details the algorithmic design and software engineering required to translate theoretical bot detection into a high-performance, edge-deployable network architecture. Engineered to guarantee memory safety and sub-millisecond execution, the system is divided into two primary, interconnected components: a Heuristic Proxy that evaluates incoming traffic via bounded-memory Log-Odds classification, and a Dynamic Traffic-Aware Cache (DTAC) that leverages randomized eviction, dual-stage Ghost caching, and resource-specific time-decayed scoring to prevent automated cache pollution. By seamlessly integrating continuous probabilistic trust scores with advanced, lock-sharded memory management, this methodology establishes a cohesive pipeline capable of mitigating volumetric AI scrapers in strict $\mathcal{O}(1)$ time complexity, ensuring that origin server performance remains uncompromised for legitimate human users.

\subsection{The Heuristic Proxy and AI-Score Generator}
The Heuristic Proxy acts as the initial ingress point for all network traffic. Its primary function is to classify incoming HTTP requests probabilistically without relying on heavy client-side challenges. To achieve sub-millisecond execution speeds, this was implemented through a Composite Trust Scoring architecture relying on a continuous Log-Odds model rather than rigid binary thresholds \cite{chandra_composite_2026}.

\textbf{The Bounded-Memory State Manager:}
To evaluate behavioral anomalies across a session without succumbing to memory exhaustion from internet-scale traffic, the proxy abandoned traditional unbounded \texttt{HashMap}s. Instead, the State Manager implemented the Space-Saving algorithm \cite{metwally_efficient_2005} to address the ``Top-K Elephant Flow'' problem commonly encountered in network measurement (Gong et al., 2018). By utilizing a Rust \texttt{HashMap} paired with a \texttt{BTreeSet}, the proxy maintained strict bounds on memory ($\mathcal{O}(1)$ space, $\mathcal{O}(\log K)$ updates). This probabilistic data structure naturally evicts low-volume legitimate users (``mice flows'') while permanently anchoring high-velocity bots (``elephant flows'') in memory.

Within this bounded state, the proxy tracked request velocity using an Exponentially Weighted Moving Average (EWMA). Because human request inter-arrival times naturally follow heavy-tailed distributions characterized by micro-bursts \cite{li_queuing_2018}, the proxy maintained an instantaneous velocity score $v$ using a time-decayed counter rather than rigidly storing timestamp arrays. Leveraging base-2 bitwise shifts, an IP's velocity score was effectively halved for every second of idle time, seamlessly accounting for natural human burstiness while harshly penalizing sustained automated scraping in strict $\mathcal{O}(1)$ execution time.

\textbf{The AI-Score Generation (Log-Odds Classification):}
Instead of a rudimentary weighted sum, the proxy calculated an aggregate penalty utilizing Naive Bayes classification converted to Log-Odds. This allowed the proxy to begin with a baseline prior probability of automated traffic ($L_0$) and perform highly efficient additive math.

For every triggered heuristic $i$, a pre-computed weight $W_i$ was added to the running log-odds score. This weight represents the log-likelihood ratio of observing the evidence $E_i$ from a bot versus a human:

\begin{equation}
W_i = \ln\left(\frac{P(E_i \mid \text{Bot})}{P(E_i \mid \text{Human})}\right)
\end{equation}

The heuristic evaluation engine processed multiple concurrent triggers:
\begin{itemize}
    \item \textbf{Passive Structural Anomalies:} The proxy applied the ``Shy Guys'' heuristic \cite{van_boxem_shy_2026}, heavily penalizing sessions that fetched HTML documents but subsequently failed to request auxiliary assets like \texttt{favicon.ico}. Additional penalties were applied for missing or misordered HTTP headers (e.g., \texttt{Accept-Language}).
    \item \textbf{Infrastructure Origin:} Cross-referencing incoming connections with Datacenter ASN databases (e.g., AWS, DigitalOcean) to isolate non-residential traffic, a proven baseline filter in automated traffic detection \cite{martinez_llamas_balancing_2025}.
    \item \textbf{Graded Request Velocity:} Rather than applying a binary step-function \cite{duskin_distinguishing_2009}, the instantaneously tracked EWMA velocity $v$ applied a continuously scaling penalty rooted in the Weber-Fechner Law. Once a baseline human burst threshold $v_{\tau}$ was exceeded, a graded log-weight was applied:
\end{itemize}

\begin{equation}
W_{velocity} = \max\left(0, \alpha \cdot \ln\left(\frac{v}{v_{\tau}}\right)\right)
\end{equation}

(Note: In the Rust implementation, this natural logarithm curve was approximated using base-2 integer logarithms via hardware-level bit counting to ensure branchless, nanosecond execution).

Once all heuristic weights were summed ($L = L_0 + \sum W_i$), the final log-odds score was converted back to a continuous probability metric $P(\text{bot})$ ranging from 0.0 to 1.0 using the sigmoid function:

\begin{equation}
P(\text{bot}) = \frac{1}{1 + e^{-L}}
\end{equation}

This calculated float value accurately reflected the confidence of an AI scraper origin. It was subsequently appended to the request payload as an HTTP header (e.g., \texttt{X-Bot-Probability}) and forwarded to the downstream cache.

Algorithm 1 illustrates the complete ingress pipeline, demonstrating how the bounded-memory Space-Saving structures and Log-Odds heuristic scoring operate synchronously for each incoming request.

\begin{verbatim}
Algorithm 1: Ingress Proxy Pipeline & Log-Odds AI-Score Generation
-------------------------------------------------------------------
Input: incoming_request
Global State: 
    SpaceSaver: Bounded-memory tracker (HashMap + BTreeSet)
    L_0: Baseline Prior Log-Odds (e.g., 0.0 for 50/50 probability)
    W_asn, W_fav, W_hdr: Pre-computed log-likelihood weights

1:  client_ip <- incoming_request.IP
2:  current_time <- current_timestamp_seconds()
3:  
4:  // --- PHASE 1: State Retrieval & Bounded Memory Management ---
5:  // SpaceSaver O(1) fetch, or evicts the lowest-volume "mouse" IP if full
6:  ip_state <- SpaceSaver.get_or_add_and_evict(client_ip)
7:  
8:  // --- PHASE 2: EWMA Velocity Calculation (Bitwise) ---
9:  delta_t <- current_time - ip_state.last_seen
10: if delta_t > 10 then
11:     new_velocity <- 1024 // Decayed to 0, plus 1 request (scaled by 1024)
12: else
13:     decayed_v <- ip_state.velocity >> delta_t  // Bitwise right-shift
14:     new_velocity <- decayed_v + 1024
15: end if
16: 
17: // Commit updated state back to memory
18: ip_state.last_seen <- current_time
19: ip_state.velocity <- new_velocity
20: SpaceSaver.update(client_ip, ip_state)
21: 
22: // --- PHASE 3: Log-Odds Heuristic Evaluation ---
23: score <- L_0
24: 
25: // Heuristic A: Continuous Graded Velocity Penalty
26: float_v <- new_velocity / 1024.0
27: if float_v > BURST_THRESHOLD then
28:     score <- score + (ALPHA * ln(float_v / BURST_THRESHOLD))
29: end if
30: 
31: // Heuristic B: Infrastructure Origin (Datacenter ASN)
32: if ASN_Database.is_datacenter(client_ip) then
33:     score <- score + W_asn
34: end if
35: 
36: // Heuristic C: "Shy Guys" Passive Behavioral Check
37: if ip_state.missing_auxiliary_assets == TRUE then
38:     score <- score + W_fav
39: end if
40: 
41: // Heuristic D: Anomalous/Missing Headers
42: if incoming_request.missing_header("Accept-Language") then
43:     score <- score + W_hdr
44: end if
45: 
46: // --- PHASE 4: Sigmoid Conversion & Forwarding ---
47: bot_probability <- 1.0 / (1.0 + exp(-score))
48: 
49: forward_to_DTAC_Cache(incoming_request, bot_probability)
\end{verbatim}

\subsection{The Dynamic Traffic-Aware Cache (DTAC) Engine}
The second component of the system is the DTAC engine, positioned upstream of the origin server. Rather than utilizing deterministic eviction algorithms (such as LRU or LFU) which either fail to account for long-term popularity or suffer from sequential scan pollution under bot traffic \cite{zhang_rethinking_2026}, the DTAC engine was implemented using a Randomized Eviction architecture combined with a resource-specific Exponentially Weighted Moving Average (EWMA) and a metadata-only Ghost Cache.

\textbf{Resource-Based EWMA \& Lock Sharding:}
Unlike the State Manager (Section 3.4.1), which tracks the behavioral velocity of client IP addresses, the DTAC engine tracks the popularity score of the requested resources (e.g., specific URLs or assets). 

When a cached resource experiences a hit, its frequency score is updated. To immunize the cache against sequential bot scans, the increment value is inversely proportional to the AI-Score generated by the proxy. A request with a 0.0 bot probability adds a full +1.0 to the resource's score, whereas a highly suspicious request adds effectively zero. Over time, the score exponentially decays based on elapsed time ($\Delta t$). Consequently, once-popular content that is no longer being requested naturally decays toward zero.

Updating this resource score on every read introduces a known concurrency bottleneck: the ``read-path write penalty.'' To prevent thousands of concurrent threads from blocking one another while updating the metadata of a highly popular asset, the system implements lock sharding via a hashing algorithm. Incoming requests are hashed to a specific concurrency bucket (e.g., one of 256 independent mutex locks). Threads only acquire the specific lock corresponding to their resource's hash, drastically reducing thread contention and maintaining ultra-high read throughput.

\textbf{Cold-Start Mitigation via Metadata-Only Ghost Cache:}
To resolve the ``Cold Start'' problem—where brand new items are evicted before they can establish a popularity score—while strictly conserving memory, DTAC implements a dual-stage architecture inspired by the S3-FIFO caching model \cite{yang_fifo_2023}.

When an initial cache miss occurs, the system does not fetch and store the full data payload. Instead, it only stores the resource's identifier and its initial score inside the Ghost Cache (a lightweight, metadata-only structure). If the resource receives subsequent requests and its decayed score crosses a predefined promotion threshold, it graduates. Only at this point is the actual data payload fetched from the origin server and stored in the Main Cache. This effectively filters out one-off scraper requests without wasting memory on their corresponding payloads.

\textbf{The Eviction Tournament (The Power of N Choices):}
When the Main Cache reaches capacity, the system triggers a randomized eviction tournament. It avoids maintaining a globally sorted priority queue entirely. The algorithm selects $N$ random items from the cache, lazily calculates their currently decayed EWMA scores on the fly, and evicts the item with the absolute lowest score. This approach heavily mirrors modern eviction frameworks like Google's HALP (Google Research, 2023) and RankCache (Beckmann et al., 2018). While this introduces a minor statistical variance compared to sorting the entire cache, the computational overhead of eviction drops to zero, ensuring $\mathcal{O}(1)$ scaling regardless of cache size.

\begin{verbatim}
Algorithm 2: DTAC Eviction, Lock Sharding, and Ghost Cache
-------------------------------------------------------------------
Input: requested_resource, request_bot_prob (Float 0.0 to 1.0)
Parameters: N_SAMPLES = 5, PROMOTION_THRESHOLD = 2.0
State: MainCache (Payloads), GhostCache (Metadata only)

1:  // Phase 1: Concurrency Management (Lock Sharding)
2:  shard_id <- hash(requested_resource) % NUM_SHARDS
3:  acquire_lock(shard_id)
4:
5:  // Phase 2: Cache Hit Evaluation & Score Update
6:  if MainCache.contains(requested_resource) or GhostCache.contains(...) then
7:      meta <- get_metadata(requested_resource)
8:      
9:      // Time-Decay (Bitwise Shift) and AI-Score Integration
10:     delta_t <- current_time - meta.last_accessed
11:     decayed_score <- meta.score >> delta_t 
12:     new_score <- decayed_score + (1.0 - request_bot_prob)
13:     update_metadata(requested_resource, current_time, new_score)
14:     
15:     // Promotion from Ghost Cache to Main Cache
16:     if GhostCache.contains(req_resource) and new_score >= PROMOTION_THRESHOLD then
17:         payload <- fetch_from_origin(requested_resource)
18:         if MainCache.is_full() then
19:             execute_eviction_tournament()
20:         end if
21:         
22:         MainCache.insert(requested_resource, payload, new_score)
23:         GhostCache.remove(requested_resource)
24:     end if
25:     
26:     release_lock(shard_id)
27:     return
28: end if
29: 
30: // Phase 3: Cache Miss (Ghost Cache Insertion)
31: // Do not store payload yet to conserve storage space
32: initial_score <- (1.0 - request_bot_prob)
33: GhostCache.insert(requested_resource, current_time, initial_score)
34: payload <- fetch_from_origin(requested_resource)
35: 
36: release_lock(shard_id)
37: return payload
38:
39: // --- Helper Function: Eviction Tournament ---
40: function execute_eviction_tournament():
41:     candidates <- MainCache.get_random_samples(N_SAMPLES)
42:     min_score <- INFINITY
43:     eviction_target <- NULL
44:     
45:     for each item in candidates do
46:         delta_t <- current_time - item.last_accessed
47:         current_decayed_score <- item.score >> delta_t
48:         
49:         if current_decayed_score < min_score then
50:             min_score <- current_decayed_score
51:             eviction_target <- item
52:         end if
53:     end for
54:     
55:     MainCache.evict(eviction_target)
\end{verbatim}

\subsection{Tuning Parameters and System Calibration}
The efficacy of both the Heuristic Proxy and the DTAC engine relies heavily on the calibration of their mathematical thresholds. Because internet traffic follows heavy-tailed Zipfian distributions \cite{breslau_web_1999}, hardcoded values inevitably lead to either excessive false positives (blocking humans) or severe cache pollution. The system's parameters must be tuned empirically based on the target network's traffic baseline.

The configuration is governed by three primary categories, with default values derived from caching literature and probability theory.

\textbf{1. Velocity and Bounded-Memory Thresholds (State Manager)}
The parameters governing the Exponentially Weighted Moving Average (EWMA) and the Space-Saving data structures dictate the proxy’s sensitivity to automated scrapers.
\begin{itemize}
    \item \textbf{Human Burst Threshold ($v_{\tau}$):} The baseline request velocity below which no penalty is applied. A standard browser loading an HTML page naturally triggers a concurrent burst of secondary assets (CSS, JS, images). Based on HTTP/2 multiplexing behaviors, a default of $v_{\tau} = 15$ to $30$ requests per second is recommended. Values below this threshold risk penalizing legitimate users on fast connections.
    \item \textbf{Velocity Scaling Factor ($\alpha$):} Determines the aggressiveness of the continuous Log-Odds penalty once an IP exceeds $v_{\tau}$. A steeper scaling factor rapidly cripples distributed botnets that attempt to pace their scraping just above human thresholds. Empirical testing suggests a default of $\alpha = 2.5$ to $3.0$.
    \item \textbf{Ghost Cache Promotion Threshold:} The required EWMA score a resource must accumulate in the metadata-only Ghost Cache before its payload is fetched from the origin server. A default of $2.0$ ensures that an asset must be requested at least twice by highly trusted users (or more times by moderately suspicious users) before consuming Main Cache memory.
\end{itemize}

\textbf{2. Probabilistic Heuristic Weights (Log-Odds Engine)}
The AI-Score Generator utilizes Bayesian probability, requiring the weights to reflect the actual log-likelihood of traffic distributions.
\begin{itemize}
    \item \textbf{Prior Probability ($L_0$):} The baseline assumption of automated traffic. For a heavily targeted public API where 60\% of traffic is automated, the prior log-odds initialization is $L_0 = \ln(0.60 / 0.40) = +0.405$. For standard web applications, a neutral $L_0 = 0.0$ (assuming a 50/50 split) is used as the default baseline.
    \item \textbf{Evidence Weights ($W_i$):} The penalty for each triggered heuristic must be calculated as $W_i = \ln(P(E_i \mid \text{Bot}) / P(E_i \mid \text{Human}))$. If a network naturally serves a high volume of enterprise VPN users, the weight for datacenter IP heuristics must be decreased to limit false positives.
\end{itemize}

\textbf{3. Eviction Tournament Sample Size ($N$)}
The most critical parameter in the DTAC engine is $N$, the number of random items sampled during an eviction tournament. If $N$ is too small, the system risks evicting a highly popular item. If $N$ is too large, the proxy wastes CPU cycles evaluating decayed EWMA scores, defeating the purpose of randomized eviction.

To determine the mathematically optimal $N$, we utilize the framework of Order Statistics to evaluate the expected value of the minimum, $E[X_{(1)}]$. In a cache, the distribution of item scores is typically bimodal: a large cluster of low-scoring ``junk'' items (decayed or one-off requests) and a smaller cluster of high-scoring popular items. This can be modeled as a Gaussian Mixture Model (GMM).

While there is no clean algebraic formula for the exact expected minimum of a GMM, we can logically determine the ``sweet spot'' for $N$. As $N$ increases, the expected minimum drops sharply at first but then hits a point of extreme diminishing returns. This bottleneck occurs because once the algorithm successfully draws at least one sample from the ``lower mode'' (the junk items), the minimum is effectively bounded by that lower distribution.

Therefore, selecting $N$ is a function of confidence. Let $p$ be the proportion of the cache population that belongs to the lower distribution (evictable items). The probability of failing to pick from this lower distribution in $n$ tries is $(1-p)^n$. The probability $P$ of successfully sampling the lower distribution at least once is:

\begin{equation}
P = 1 - (1-p)^n
\end{equation}

To find an $N$ that guarantees a specific confidence interval, we solve for $n$:

\begin{equation}
n = \frac{\ln(1 - P)}{\ln(1 - p)}
\end{equation}

\textit{Calculating the Default $N$:} Suppose the cache is heavily utilized, and only 20\% of the cache consists of optimally evictable junk items ($p = 0.20$). To be 95\% confident ($P = 0.95$) that the random sample includes at least one of these ideal eviction candidates, the required sample size is:

\begin{equation}
n = \frac{\ln(1 - 0.95)}{\ln(1 - 0.20)} = \frac{\ln(0.05)}{\ln(0.80)} = \frac{-2.995}{-0.223} \approx 13.4
\end{equation}

By setting $N = 14$, the system mathematically guarantees a 95\% probability of finding a highly decayed item without the $\mathcal{O}(N)$ overhead of sorting the entire cache.

For environments where the cache churn is higher and junk items make up a larger proportion of the cache (e.g., $p = 0.50$), the required sample size drops drastically. Achieving 95\% confidence in this scenario requires only $N = 5$ ($1 - 0.5^5 = 0.968$). This aligns with the default parameters established by industry implementations; Redis utilizes $N = 5$ for its \texttt{allkeys-lfu} policy as an optimal balance between CPU efficiency and eviction accuracy (Redis Core Architecture).

\section{Workload Simulation and Data Generation}
Testing caching algorithms against a live production server introduces uncontrolled variables—such as network latency spikes, sudden hardware throttling, and unpredictable user behavior—that make precise metric evaluation nearly impossible. To ensure that the performance of the DTAC algorithm was accurately and reproducibly measured, it was necessary to generate synthetic, mathematically verifiable workloads. Custom Rust scripts were developed to synthesize HTTP request logs that accurately reflected the behavioral dichotomies between human users and automated bots.

\subsection{Simulating Legitimate Human Traffic}
Human web browsing naturally exhibits temporal locality and highly skewed popularity patterns, heavily favoring a small subset of ``hot'' web pages. To mathematically simulate this behavior, the data generator synthesized human requests following a Zipfian distribution \cite{breslau_web_1999}.

In a Zipfian distribution, the probability $P(k)$ of a request for the $k$-th most popular web object out of a total catalog size of $N$ items is defined as:

\begin{equation}
P(k) = \frac{1/k^\alpha}{\sum_{n=1}^{N} (1/n^\alpha)}
\end{equation}

For the simulation, the catalog size ($N$) was established at 100,000 unique web objects. The skewness parameter ($\alpha$), which dictates the intensity of the popularity concentration, was set to 0.8, a standard baseline for mirroring realistic human web traffic. These generated requests were paired with standard HTTP headers (e.g., valid \texttt{User-Agent} strings, \texttt{Accept-Language}, and subsequent requests for \texttt{favicon.ico}) to ensure the Heuristic Proxy correctly classified them as benign with a low AI-score.

\subsection{Simulating AI Scraper Traffic}
Conversely, automated AI scrapers and LLM data harvesters utilize ``scan'' patterns characterized by high-volume, single-use access over broad swaths of a website \cite{zhang_rethinking_2026}. To simulate this, the bot workload was generated using a uniform distribution over a separate subset of the catalog space. In a uniform distribution, the probability of requesting any specific item is equal, resulting in near-zero temporal recurrence and effectively mimicking the one-hit-wonder behavior of scrapers.

To trigger the Heuristic Proxy's passive detection, these requests were imbued with mechanical signatures. The simulated bot logs included anomalies such as:
\begin{itemize}
    \item The deliberate omission of secondary asset requests (e.g., fetching an HTML document but skipping the \texttt{favicon.ico}).
    \item Missing or malformed \texttt{Accept-Language} and \texttt{Sec-CH-UA} headers.
    \item Highly consistent, mechanical inter-arrival request timings that deviate from the bursty nature of human clicking.
\end{itemize}

\subsection{Traffic Mixing and Ratios}
To evaluate the DTAC system under varying levels of infrastructure strain, the generator script blended the Zipf-distributed human logs and the uniformly distributed bot logs into chronological, single-stream request logs.

The traffic was multiplexed to create multiple distinct datasets, each representing a different severity of AI interference. The test ratios were defined by the percentage of total traffic originating from simulated scrapers:
\begin{itemize}
    \item \textbf{10\% Bot Traffic:} Representing a baseline, low-threat environment.
    \item \textbf{30\% Bot Traffic:} Representing moderate, localized scraper activity.
    \item \textbf{50\% Bot Traffic:} Representing a heavy data-harvesting event.
    \item \textbf{75\% Bot Traffic:} Representing a catastrophic scan event capable of inducing severe cache thrashing \cite{zhang_rethinking_2026}.
\end{itemize}

These distinct, pre-compiled datasets were saved to the NVMe SSD, providing deterministic and repeatable inputs for the Log Replayer during the final benchmarking procedures.

\section{Experimental Setup and Benchmarking Procedures}
To empirically validate the efficacy of the DTAC algorithm against standard caching mechanisms, a rigorous benchmarking protocol was established. The experiments were executed on the dedicated cloud bare-metal server (detailed in Section 3.3.1) to ensure unconstrained I/O performance and prevent hardware bottlenecks during high-concurrency log replays.

\subsection{The Benchmarking Protocol}
The lifecycle of each individual experiment followed a strict three-step protocol to ensure that the data collected accurately reflected real-world production environments rather than artificial testing anomalies.

\begin{enumerate}
    \item \textbf{Step 1: Cache Warm-Up:} A cache starting from an empty state (a ``cold'' cache) naturally experiences an initial 100\% miss rate as it begins storing objects, which heavily skews performance metrics. Therefore, before introducing any simulated scraper traffic, the system was ``warmed up.'' The Log Replayer streamed an initial batch of pure Zipf-distributed human requests into the proxy. This process continued until the cache reached its absolute maximum memory capacity, simulating a realistic, steady-state production environment where memory is fully utilized and eviction logic is actively engaged.
    \item \textbf{Step 2: Mixed Traffic Injection:} Once the cache reached steady-state capacity, the Log Replayer initiated the injection of the mixed traffic datasets (detailed in Section 3.5.3). The scripts dispatched the 10\%, 30\%, 50\%, and 75\% bot-ratio logs concurrently over \texttt{localhost} to the Heuristic Proxy, effectively simulating varying degrees of infrastructure strain and AI-scraper attacks.
    \item \textbf{Step 3: Metric Logging:} Throughout the mixed traffic injection phase, the integrated Metrics Tracker passively monitored the DTAC Engine. It continuously recorded the outcome of every request—logging whether it resulted in a cache hit or a cache miss—and documented every eviction event, specifically tracking whether the evicted object originally belonged to the human or bot workload.
\end{enumerate}

\subsection{Baseline Comparison (A/B Testing)}
To isolate and quantify the performance impact of the AI-aware algorithmic modifications, an A/B testing methodology was employed. Every simulated workload ratio was systematically executed twice:

\begin{itemize}
    \item \textbf{The Control Run (Standard LRU):} The mixed dataset was first processed using the baseline Least Recently Used (LRU) algorithm. In this configuration, the cache completely ignored the appended AI-scores generated by the Heuristic Proxy, treating all incoming traffic (both human and bot) with equal temporal importance. This established the performance baseline and demonstrated how severely standard caches degrade under scan patterns.
    \item \textbf{The Experimental Run (DTAC):} The exact same mixed dataset was subsequently processed using the DTAC engine. In this configuration, the algorithm actively evaluated the AI-scores, dynamically penalizing highly probable scraper traffic by routing it directly to the eviction tail.
\end{itemize}

By ensuring that the request sequence, total cache capacity, and underlying hardware constraints remained mathematically identical across both runs, any divergence in the final performance metrics could be exclusively attributed to the introduction of the DTAC architecture.

\section{Evaluation Metrics}
To rigorously evaluate the success of the Dynamic Traffic-Aware Caching (DTAC) algorithm against the baseline LRU, the benchmarking protocol recorded a specific set of quantitative metrics. These metrics were designed to assess both the protective capability of the cache in preserving human user experience and the computational overhead introduced by the heuristic evaluations.

\subsection{Cache Efficiency Metrics}
The primary goal of the DTAC system is not necessarily to increase the overall cache hit rate, but to preserve the hit rate for legitimate human users during an active AI scraper attack. Therefore, the hit rates were isolated by traffic origin.

\textbf{Human Cache Hit Rate ($CHR_{human}$):} This was the most critical metric of the study. It measures the percentage of legitimate human requests successfully served from the cache rather than requiring a costly fetch from the origin server. It is calculated as:

\begin{equation}
CHR_{human} = \frac{H_{hit}}{H_{total}}
\end{equation}

Where $H_{hit}$ is the number of human requests found in the cache, and $H_{total}$ is the total number of human requests generated by the Zipfian workload simulator. A successful DTAC implementation will maintain a stable $CHR_{human}$ regardless of the volume of bot traffic injected.

\textbf{Overall Byte Hit Rate (BHR):} While object hit rate measures individual files, BHR measures the total volume of data served from the cache. This is a crucial metric for evaluating bandwidth and egress cost savings. It is defined as:

\begin{equation}
BHR = \frac{\sum B_{hit}}{\sum B_{total}}
\end{equation}

Where $B_{hit}$ represents the bytes served from the cache and $B_{total}$ represents the total bytes requested across the entire mixed dataset.

\subsection{Cache Pollution Index (CPI)}
To quantify exactly how much damage the simulated automated scrapers inflicted on the memory infrastructure, a Cache Pollution Index (CPI) was tracked. The CPI measures the proportion of cache memory occupied by single-use bot data at any given observation window.

\begin{equation}
CPI = \frac{M_{bot}}{M_{total}}
\end{equation}

Where $M_{bot}$ represents the number of memory nodes occupied by data originally requested by objects flagged with an AI-score exceeding the threshold $\tau$, and $M_{total}$ represents the maximum node capacity of the cache. 

During the Control Run (baseline LRU), the CPI is expected to scale linearly with the injected bot traffic ratio. During the Experimental Run, the DTAC engine's tail-insertion logic should theoretically keep the CPI near 0\%, as scraper data is immediately targeted for eviction.

\subsection{Computational Latency and Overhead}
Because the proxy and cache sit inline with the network traffic, any algorithmic modifications must not introduce severe delays. While Rust's memory safety and performance characteristics mitigate underlying execution latency, the algorithmic overhead still required strict measurement.

\begin{itemize}
    \item \textbf{Proxy Scoring Overhead ($T_{proxy}$):} The time taken for the Heuristic Proxy's State Manager to evaluate a session's history (e.g., checking for missing \texttt{favicon.ico} fetches) and calculate the normalized AI-score. Since this relies on $\mathcal{O}(1)$ \texttt{HashMap}s, $T_{proxy}$ should ideally remain below 2 milliseconds.
    \item \textbf{Cache Insertion/Eviction Overhead ($T_{cache}$):} The time required for the DTAC engine to evaluate the appended AI-score, determine the insertion position (MRU head vs. LRU tail), and update the doubly linked list pointers. Because tail insertion is an $\mathcal{O}(1)$ operation identical in complexity to head insertion, the delta in $T_{cache}$ between the baseline LRU and DTAC must be statistically insignificant.
\end{itemize}

These latency metrics were measured using Rust's high-precision \texttt{std::time::Instant} standard library module, capturing the execution time from the exact moment a request entered a functional block to the moment it was dispatched.
